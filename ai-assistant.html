AI 旅游智能助手

痛点场景

小 A 的一次出行规划

在真正动手做产品之前，先看看一个普通用户是怎么被「规划一趟旅行」这件事折磨的。

用户故事 · 小 A

国庆想去成都玩 3 天，小 A 打开大众点评翻景点评价，看到宽窄巷子不错；又切到地图 App查它离酒店多远；再打开天气 App看那几天会不会下雨；最后跳到订房页比价订酒店。

四个 App 来回切换，信息全靠手动东拼西凑；好不容易排好行程，临时想把第二天的景点换一个——结果路线、时间、预算全得重排一遍。而她真正想要的，其实只是一句话：「帮我安排好，我照着走就行。」

痛点 · 信息分散

东拼西凑

景点、天气、酒店分散在不同 App，用户要来回切换、手动整合，效率极低。

痛点 · 缺个性化

千人一面

通用攻略不考虑你的偏好、预算、出行时间等真实约束，看了还得自己改。

痛点 · 难调整

牵一发动全身

景点顺序、时间、预算相互关联，改一处往往要重排整个行程与花销。

产品流程

用户会经历的三步

从「说出需求」到「拿到一份算得清账的行程」，用户前端只需经历三个环节。

STEP 01

智能行程规划

输入目的地、日期、偏好，四个 Agent 协作产出含景点 / 餐饮 / 酒店 / 天气的完整行程。

→
STEP 02

预算计算

自动把费用拆成景点门票、酒店、餐饮、交通四大类并汇总，花销一目了然。

→
STEP 03

单次调用成本分析

核算每生成一次行程的模型成本，并通过缓存、路由等策略把它压下来。

介绍 · 智能行程规划

Agent 角色设计

为什么不用一个 Agent 干完所有事？因为提示词会爆炸、难维护、出错难定位。解法很直觉——像旅行社一样分工。点击下面的小人，看每个 Agent 的职责与它的提示词。

技术架构

四层架构，一条数据流

系统采用经典的前后端分离架构，自上而下分为四层，每层只做自己那件事。

数据流转：用户在前端填表 → 后端校验数据 → 调用智能体系统 → 三个专家 Agent 并行取数（景点 / 天气 / 酒店）→ 规划 Agent 整合生成 → 每个 Agent 通过 MCP 调用外部 API → 结果返回前端渲染。

多智能体协作流程

用户请求进来，三个专家并行取数，规划师汇总生成最终计划。

  1. 景点搜索：AttractionSearchAgent 按城市 + 偏好召回景点候选。
  2. 天气查询：WeatherQueryAgent 取未来几天天气预报。
  3. 酒店推荐：HotelAgent 按住宿类型搜索酒店。
  4. 整合生成：PlannerAgent 汇总三方结果 + 用户需求，生成完整计划。
  5. 解析 JSON：把规划师输出解析为结构化 TripPlan，返回前端。

介绍 · 成本分析

一次行程生成，到底花多少钱

AI 产品能不能规模化，账要算得清。这里核算单次调用成本，并用工程手段把它压下来。

单次 0.48 元 → 优化后 0.35 元，降本 27%
优化前 · 0.48 元 / 次
  • 输入 4500 Token + 输出 3560 Token
  • DAU 1000 时，日成本 1440 元
  • 约 $0.0661（Sonnet 定价 $3.00 / $15.00）
→
优化后 · 0.35 元 / 次
  • 缓存命中 25% + 路由 50% 走 Haiku
  • DAU 1000 时，日成本 1050 元
  • 降幅约 27%

成本优化策略

P0语义缓存（命中率 25%）→ 降本 20%–25%
P1Prompt 压缩（减少 25% 输入）→ 降本 10%–15%
P0模型路由（咨询走 Haiku）→ 降本 25%–35%
P1流式截断（15% 提前停止）→ 降本 5%–10%
